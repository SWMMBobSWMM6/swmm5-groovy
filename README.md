# swmm5-groovy

EPA SWMM 5.2.4 in Groovy, written by a translator that reads EPA's C, and judged against EPA itself: the binary
`.out` file byte for byte, and the `.rpt` report line for line except the three lines that print the wall clock.

**Result: 480 of 480 models identical**, twice: the first full gate (gv_1, 8 November 2026) and an independent
rerun from a clean checkout with the engine and the math regenerated and the jar rebuilt (gv_v, 9 November 2026):
every `.out` byte-identical, every `.rpt` identical except the three clock lines, exit code 0 on every model, as
EPA's. The 480 took 1,114 seconds of engine time in gv_1 and 792 s in gv_v, one at a time; the longest was
Hydrology/SCANLON.inp, 35.5 s in gv_1.

It is not a new engine and not a wrapper: there is no C in it and it calls no other port. It does not call the Java
or Kotlin ports' classes either; their sources were the model for parts of the runtime, as the Java back end was for
the translator. Every number it writes is EPA 5.2.4's, including the results of EPA's own defects wherever EPA's
behaviour is defined (`lessons/02-epa-defects-found.md`). Groovy is one of the eight languages of the second wave of
Bob Dickinson's Code Rosetta Stone app.

## The parity contract

The same as the earlier ports' (see `go/` or the swmm5-go repository): EPA SWMM 5.2.4 built from the USEPA v5.2.4
tag with gcc 13.3 `-O2` on x86-64 Linux with glibc 2.39 (`ref/Makefile`), on a processor with FMA and AVX2; each
model run in its own folder; pass = `.out` byte-identical (when EPA writes one) and `.rpt` identical after removing
`Analysis begun on`, `Analysis ended on` and `Total elapsed time`, the exit code the same (EPA's command line always
exits 0). When an input error stops EPA before it writes results, the engine must not write a results file either.
Corpus: the 480 gate models of `gate/models_all.tsv` from SWMMBobSWMM6/1729-SWMM5-Models-2030.

## Run

Requires a JDK 17 or newer (tested with **OpenJDK 21.0.12.1**, `openjdk version "21.0.12.1" 2026-08-18`, the Ubuntu
build) and the jars of **Groovy 3.0.24**. Nothing was downloaded: the Groovy compiler is the one Gradle 8.14.3 ships
in `/opt/gradle/lib` (`groovy-3.0.24.jar` and the ASM and ANTLR jars beside it; `GROOVY_LIB` points elsewhere).

```sh
groovy/build.sh                                   # compiles src/swmm5/*.groovy into groovy/swmm5.jar
groovy/runswmm model.inp model.rpt model.out
```

`build.sh` runs Groovy's `FileSystemCompiler` on the 59 source files. Every class is `@CompileStatic`, so at run time
the jar needs only `groovy-3.0.24.jar` beside it (for the few runtime helpers static Groovy still calls).
`runswmm` is a shell launcher for `java` with three flags: `-XX:-DontCompileHugeMethods` (below, under Speed),
`-XX:+UseParallelGC -XX:MaxRAMPercentage=75` (one corpus model allocates 3.38 GB of RDII rainfall history, as EPA
itself does, and the JVM's default heap is a quarter of memory: lessons/14, as in the Java and Kotlin ports).

To regenerate the engine: `python3 tools/c2x/emit_groovy.py groovy/src/swmm5` from the repository root (needs
`pip install libclang==18.1.1` and the clang 18 headers at `/usr/lib/llvm-18/lib/clang/18/include`). To regenerate
the math: `groovy/make_glibm.sh GIMPLE_DIR TABLES_JSON` (the outputs of `tools/libm/build_glibm.sh` and
`extract_tables.py`; the default is the build kept at `/home/claude/ext/glibm_build`).

## How it was made

`tools/c2x/front.py` parses EPA's C with libclang; `tools/c2x/emit_groovy.py` subclasses the Java back end
(`emit_java.py`) and keeps its analysis and type model unchanged, because Groovy compiles to the same JVM: `char*` is
a `CPtr`, a scalar pointer parameter is a reference object, a local whose address is taken is a box, `unsigned int`
is a `long` masked to 32 bits, a double goes to an int through `R.D2I` (x86's rule, not the JVM's saturating cast),
structs are classes with `copy()`. Most of Java's syntax is also Groovy's; what Groovy does differently is where the
work was, and each item is written out in the emitter's header:

- **Numbers.** A decimal literal without a suffix is a `BigDecimal`, so every double literal carries `d`; `-0.0d` is
  folded to +0.0, so C's negative zero is `R.NZ`; `/` on two ints gives a `BigDecimal`, so C's integer division is
  `R.idiv`/`R.ldiv`; `float * float` is computed in double, so each float operation is rounded back,
  `((float) (a * b))` (the same as the float operation, since a double has more than twice float's precision).
- **NaN comparisons.** `a > b` and `a >= b` on doubles compile to `dcmpg`, which makes them true when either side is
  NaN; C and Java say false. They are written `R.dgt(a, b)` and `R.dge(a, b)`, which are `b < a` and `b <= a`. Found
  on EPA/swmm5_shapes.inp, whose report listed five NaN nodes as not converging where EPA's says "Convergence obtained
  at all time steps." (`lessons/37-groovy-greater-than-is-true-for-nan.md`, `groovy/results/nan_compare.txt`).
- **Statements.** `switch` compiles to a chain of boxed `isCase()` calls, so it is an if/else-if chain on an int, with
  C's fall-through written out (as the Kotlin back end does); every loop is labelled and every `break` and `continue`
  names its target; a bare `{ }` is a closure, so nested C blocks are flattened.
- **Static compilation is not all static.** An assignment to another object's field compiles to a reflective
  `ScriptBytecodeAdapter.setProperty` call, which is slow; `x.@f = v` is a plain `putfield`, but `x.@f += v` reads
  the field reflectively, so every such store is written `x.@f = x.f op v`. `a[i] /= y` and `X::new` also compile to
  dynamic calls and are written out. The generated bytecode was searched with `javap` for the dynamic call sites
  that remained: array helpers, casts after generic returns, metaclass set-up and unreachable implicit returns.
- **Names and equality.** `==` on two objects calls `equals()` (and on arrays compares elements), so pointer identity
  is `===`; a field without a modifier is a property with a getter and setter, so every field is `public`; the
  globals `Node` and `Stack` resolved to `groovy.util.Node` and `java.util.Stack` when statically imported, so they
  are `Node_` and `Stack_` and every cross-file reference names its class (`F_project.Node_`).

When the port disagreed with EPA, the fix went into the translator or the runtime, never into the generated files.

## The runtime and the math library

- **printf, strtod, sscanf** (`R.groovy`): glibc's formatting written out, with the digits of `%f`, `%e` and `%g` from
  `BigDecimal` (exact, so ties round to even as glibc's printf does); glibc's `strtod` syntax, hexadecimal floats and
  `nan(...)` payloads included. Checked against glibc 2.39 by `groovy/test/run_crtcheck.sh` (the 1,394,252 cases from
  `tools/crt/test/mkfmt.c` that the other runtimes replay): **1 differs**, `%#g` of 999999.5 (glibc `1.e+06`), the
  case most runtimes report; SWMM never uses `%#g` (`groovy/results/crtcheck_result.txt`).
- **Math.** The JVM's `Math` functions are not glibc's (they differ in the last bit on some arguments), so the engine
  calls none of them for a transcendental function. `Glibm.groovy` is glibc 2.39's own code, the FMA variants EPA's
  build runs, translated from the GIMPLE GCC writes for it by a new Groovy back end of `tools/libm/gim2x.py`, with
  `Math.fma` for each fused multiply-add GCC placed (exact on the JVM). The back end writes expressions by the Java
  back end's rules plus the Groovy differences above (`d` literals, `R.idiv`, swapped `>` and `>=`, a binary search
  instead of a `switch` for the GIMPLE's block dispatch). `Math.sqrt`, `Math.abs` and `Math.floor` are exact on
  every platform and are used directly.
- Checked bit for bit, NaN signs and payloads included, by `groovy/test/run_libm_tests.sh` (`test/Check.groovy`, run
  with the flags `runswmm` uses): 11,000,672 random arguments over SWMM's ranges plus special values
  (`tools/libm/test/mkvectors.c`) and 3,300,000 edge cases (`mkedge.c`) for exp, log, log10, pow, sin, cos, tan,
  asin, acos, atan and fma: **0 differ** (`groovy/results/libm_tests.txt`).
- **The other back ends are unchanged.** Adding the Groovy back end to `gim2x.py` was additions only:
  `groovy/test/check_gim2x_regen.sh` regenerates the TypeScript, Java, Go, Kotlin and JavaScript translations with the
  new `gim2x.py` and compares them byte for byte with the shipped files, and regenerates the Groovy one: all
  identical (`groovy/results/gim2x_regen.txt`).

## Speed

The gate's clock: gv_1 took 1,114 seconds of engine time for the 480 models (18.6 minutes of wall time), one at a
time, on a 2-core machine shared with other agents' runs; the longest were Hydrology/SCANLON.inp, 35.5 s, and
EPA/72_H&H_Elements(2).inp, 33.9 s. gv_v, the same code rebuilt, took 792 s (13.3 minutes): the load of the shared
machine moves the gate's clock by that much. The Kotlin port's first gate took 397 s on the same machine at another
time, so no ratio is claimed; no interleaved benchmark against EPA was run (lessons/07).

One setting matters a great deal. HotSpot never JIT-compiles a method of more than 8,000 bytes of bytecode, and
Groovy's translations of pow (9,161 bytes), acos, tan and asin are over that line, where javac's are not (pow: 5,558
bytes). With the default, SCANLON ran for more than 380 s without finishing, every pow call interpreted; with
`-XX:-DontCompileHugeMethods` it took 32.6 s, identical to EPA (`groovy/results/hugemethod.txt`,
`lessons/38-hotspot-will-not-compile-a-huge-method.md`). The flag changes which code is compiled, not what it
computes.

## What this does not show

- That SWMM is right: identical to EPA means EPA's answers, good or bad.
- Other platforms: the math is glibc's code translated, so it should give EPA-on-x86-64 answers wherever a JVM runs,
  but only x86-64 Linux with OpenJDK 21 was run. The JVM's arithmetic is IEEE and strict (no fused operations unless
  written as `Math.fma`), which is what that expectation rests on.
- Other Groovy versions: only 3.0.24 was run. The traps above are properties of its static compiler, and each would
  need checking again under another version.
- Paths no gate model exercises: streets and inlets (one deck, which stops on input errors), climate files, USE
  HOTSTART, USE INFLOWS, USE RUNOFF; the stepping API is translated but only the command line was gated.
- A checked run in C's sense: the JVM catches every out-of-range array index, but a C overrun that stays inside an
  array's bounds would not show; the gate would see it only if it changed an output.
- No person has reviewed the generated code line by line; the evidence is the gate and the runtime checks.
